# Executable mechanism discovery orientation

This experimental task family is new. There is no assumed benchmark pattern
for solving it. Do not silently substitute ordinary curve fitting,
retrospective explanation, feature importance, or report writing for the
requested task.

The scientific claim is the sealed executable mechanism. The report explains
and cites that claim, but it is not a replacement for it.

## Required transformation

```text
validated generation facts
        |
        v
candidate mechanism variables
        |
        v
state-sufficiency and closure tests
        |
        v
executable state + update law
        |
        v
multiple prefix-only falsification tests
        |
        v
sealed model -> unseen continuous execution
```

The objective is not the smallest possible state. The objective is the
simplest state that remains sufficient for the declared predictions and
interventions. A compact model that omits a state variable which continues to
affect future behavior is not a successful reduction.

## 1. Separate explanation from execution

An observed run can support a detailed explanation after the relevant outcome
has occurred. An unseen-prefix forecast is different: it must update from the
prefix state without reading the future.

For every variable described as causally important in the report, do one of
the following:

1. include it in the executable state or update law; or
2. give a falsification result showing that it can be eliminated without
   changing the required future predictions.

Do not cite a rich set of graph facts in the report and then silently replace
them with a much smaller empirical trend in the executable.

## 2. Test state sufficiency

Let the proposed executable state at a cut be `q`, the declared input be `a`,
and the next state and outcome be `(q_next, y_next)`. A candidate state is
operationally closed only if equal or sufficiently similar `(q, a)` cases do
not produce materially incompatible `(q_next, y_next)` behavior under the
required tolerance.

Use the discovery graph to search for counterexamples:

- similar proposed state, different next behavior;
- a supposedly irrelevant graph variable that separates those cases;
- a variable that continues to evolve while the proposed state is held;
- a state transition that cannot be generated by the submitted update law.

If such a counterexample exists, enlarge or revise the state. Do not hide the
failure by broadening the narrative.

## 3. Use prefix-only replay before sealing

Choose multiple historical cut points in the discovery execution. For each
cut:

1. expose only the graph prefix at or before that cut;
2. initialize the candidate from that prefix;
3. predict a later interval without reading its graph facts;
4. compare the prediction with the already recorded discovery suffix;
5. retain failures and revise or reject the mechanism.

Include cuts before, near and after any proposed state transition when those
regions exist. A full-run fit is not a substitute for prefix-only replay.

## 4. Compile the report into code

Before submission, make an internal correspondence table:

| Mechanism claim | Primitive GFG evidence | Executable state field | Update-law location |
|---|---|---|---|
| claimed variable or transition | exact facts/relations | field name, or justified elimination | function/equation |

Every mechanism claim that affects a required forecast must have an
executable representation. Every executable field must have a defined update
or be a frozen constant derived only from the allowed prefix.

Field presence is not operational use. A variable that is read, serialized,
reported or carried forward but cannot change a required prediction is a
diagnostic, not part of the operative mechanism. Before sealing, perform an
executable-use audit:

1. list every field claimed to control formation, transition, stability or an
   intervention response;
2. identify the exact executable expression through which that field can
   alter the forecast;
3. perturb, remove or hold the field fixed in prefix-only replay when the
   evidence permits, and check whether the claimed effect changes;
4. relabel fields with no operational effect as diagnostics, or revise the
   update law so that the supported state dependence is actually executed.

Reject a candidate whose rich mechanism narrative compiles to a forecast
controlled only by an absolute step, a threshold timestamp, a fixed delay or
another single-run clock regularity, unless the discovery evidence and
falsification tests support that clock as the required invariant. Prefer a
prefix-conditioned state law when the graph exposes state that distinguishes
different remaining futures.

Treat post-formation stability as its own state-closure problem, not as an
auxiliary label added after the formation forecast is complete. Before
sealing:

1. initialize the proposed stability state immediately before multiple
   observed degradation, persistence and recovery regions;
2. search for histories with the same proposed compressed stability state
   but different subsequent behavior;
3. if such a counterexample exists, retain additional state that distinguishes
   the futures and make that state operational in the executable update law;
4. derive the intervention's stability direction from that same update law.

For this task family, one sealed theory must contain two explicit executable
submodels. `FormationDynamics` represents how the capability is formed.
`StabilityDynamics` represents how the already formed capability is retained,
degraded and recovered. They may share declared inputs and state, but neither
may be replaced by a label, an interval list or prose. The unified mechanism
must execute both submodels over the entire requested future grid and compose
their outputs as

```text
predicted validation = clamp(formation capability - stability degradation,
                             0, 1)
```

The purpose of this decomposition is operational accountability, not an
assumption that the two mechanisms are causally independent.
After formation, do not hide a predicted loss of the formed capability by
lowering the formation output while leaving stability degradation at zero.
Post-formation deficits must be produced by the executable stability state and
update law.

A stability model is not complete merely because it predicts the next dip.
Its recursively updated state must generate the location, duration, amplitude
and recovery of degradation over the full requested horizon. Test it at cuts
before several distinct degradation and recovery regions. Compare the entire
held-out stability-deficit curve, not only the nearest event. If one state
summary predicts many false degradation windows, misses later episodes or
requires a precomputed calendar of future cycles, it has not established a
transportable stability law.

A fixed time difference, growth rate, state increment, threshold, cycle
number or cycle parity observed in one discovery execution is not by itself a
transportable stability law. It may be retained only when prefix-only tests at
multiple comparable states support its prospective use. This rule does not
identify any target state variable, event time, threshold or answer.

The code may be more complex than a familiar low-dimensional curve model.
Prefer adequacy over cosmetic simplicity. It may still be rejected if it is
only a stored trajectory or identifies a particular run.

## 5. Audit intervention completeness

An intervention may hold one visible quantity constant while other internal
states continue to update. Before predicting an intervention effect:

1. enumerate every mechanism state read or written by the affected operation;
2. determine which of those states the hook actually changes, freezes, or
   leaves evolving;
3. propagate those differences through the submitted update law;
4. test the intervention on discovery-run prefixes when the hook permits it;
5. reject claims of pure time translation unless all state needed for that
   claim is shown to translate consistently.

This rule is domain-neutral. It does not identify which variables matter in
the target execution.

## 6. Distinguish invariant law from one-run regularity

A repeated pattern in one trajectory is a hypothesis, not automatically a
cross-run mechanism. Identify which parts of the submitted model are:

- fixed structural laws;
- state inferred from the supplied prefix;
- parameters estimated from the discovery execution;
- uncertainty caused by limited observations.

Attempt to falsify fixed-period, fixed-amplitude and constant-rate assumptions
before using them outside the discovery run.

Correct state semantics do not by themselves establish a correct cross-run
state-transition law. Cross-run transport must not be carried directly by a
fixed time difference, fixed growth rate, fixed period or fixed state increment
observed in one discovery execution. At multiple historical prefix cuts,
prospectively test the proposed state and update law and search for comparable
cases with similar compressed state and declared external inputs but materially
different futures. Such a counterexample means that the compressed state or its
update law is insufficient; retain additional state, input or mechanism context
that distinguishes the futures. Passing these within-run tests means only that
the candidate was not falsified by the discovery execution. A mechanism claimed
to transport across executions must still be sealed and tested prospectively on
a distinct unseen continuous execution.

## Unrelated toy counterexample

Suppose a toy generator reports output `y` and accepts command `c`. A model
fits `y_next = y + c` on the observed run. The generator also contains an
internal accumulator `h` that updates every execution and affects `y` only
after a threshold. The fitted model explains the observed prefix but is not
closed because two equal `(y, c)` states with different `h` have different
futures. Holding `y` fixed does not hold `h` fixed.

The correct lesson is not that every hidden variable must be retained. It is
that elimination requires a counterexample search and an operational closure
test.

## Orientation self-check

Before target evidence is released, be able to state:

- why the executable model, not the report, is the scientific authority;
- how state sufficiency is tested;
- how multiple prefix cuts prevent retrospective fitting;
- how each report claim is mapped into executable state and code;
- why storing a state field is not the same as making it operational in the
  forecast, and how to audit that distinction;
- why an intervention must audit all state that can continue to evolve;
- why a repeated pattern in one run is not automatically invariant;
- why correct state semantics do not by themselves establish a transportable
  state-transition law, and how matched-state divergent-future counterexamples
  expose an insufficient state compression.
- why formation and post-formation stability require distinct executable
  states and update laws even though one unified theory composes their outputs.

This guide defines a method. It supplies no target mechanism, target state,
future trajectory, intervention answer, or hidden evaluation result.
