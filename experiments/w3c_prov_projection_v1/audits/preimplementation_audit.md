## Seventeen required answers

1. **Entity, Activity, Agent.** Entity is a thing with fixed aspects; Activity is something occurring over time that acts upon or with entities; Agent bears responsibility for activities, entities, or other agents' activities. A `GeneratorManifest` therefore projects to `prov:SoftwareAgent`.

2. **Generation, Usage, Derivation.** Generation is completion of production of an Entity by an Activity. Usage is the beginning of an Activity utilizing an Entity. Derivation asserts that a used Entity influenced the creation or transformation of a generated Entity; shared use and generation alone do not imply derivation.

3. **Identified relations.** PROV-N places a relation identifier before the semicolon in `used`, `wasGeneratedBy`, and `wasDerivedFrom`. This profile always identifies Usage, Generation, and Derivation.

4. **Expanded derivation.** It cites the generated Entity, used Entity, Activity, the identified Generation, and the identified Usage. The latter two must exist and agree with the participants.

5. **Applicable constraints.** Constraint 23 checks identified-relation key consistency; Constraint 24 generation uniqueness; Inference 11 derivation/usage/generation closure; Constraint 50 typing; Constraint 51 disallows generation/usage parameters with unspecified activity; Constraint 53 rejects impossible overlaps. Temporal ordering is `NOT_EVALUATED` because Start, End, event times, and temporal ordering are excluded. Profile validators separately require every selected reference to resolve.

6. **Qualified PROV-O.** `prov:qualifiedUsage` points from Activity to `prov:Usage`, which cites `prov:entity`; `prov:qualifiedGeneration` points from Entity to `prov:Generation`, which cites `prov:activity`; `prov:qualifiedDerivation` points from Entity to `prov:Derivation`, which cites `prov:entity`, `prov:hadActivity`, `prov:hadGeneration`, and `prov:hadUsage`. Association uses `prov:qualifiedAssociation` and `prov:agent`.

7. **Unambiguous Core projections.** Source Information, Generated Support, and Explicit Disposition become selected Entity subtypes; Occurrence becomes Activity; Manifest becomes SoftwareAgent; responsibility becomes Association. A binding becomes one Usage and one Derivation and shares the unique outcome/activity Generation.

8. **Excluded Core facts.** Evidence and evidence links, evidence closure, operation results, complete environment, Snapshot validation state and hashes, query indexes, registries, complete payloads and transform context, undeclared metadata, and GeneratedOrigin bridge identity/evidence/operation facts do not enter the profile.

9. **GeneratedOrigin.** When it authoritatively refers to a prior generated support, the downstream Activity uses that support's Entity directly. The bridge's independent Core occurrence identity is not projected.

10. **Disposition is not invalidation.** Invalidation means destruction, cessation, or expiry of an Entity. A Core disposition describes how source information was suppressed, unsupported, or not represented and does not assert cessation. It is an `ex:DispositionRecord` Entity generated by the Activity.

11. **Pairing and multiplicity.** The candidate projects explicit bindings only. Every Usage and Derivation has a semantic identifier; an outcome/activity pair has one shared Generation. Deterministic ordinals distinguish duplicate selected binding semantics. No Cartesian product or guessed diagonal is permitted.

12. **Extension attributes.** A closed allowlist is necessary for stable source, result, disposition, occurrence, agent, operation, role, and ordinal semantics. The exact list will be frozen in the profile before implementation.

13. **Extension boundary.** Declared stable domain semantics are legal. Complete Snapshots, Core records/tables, Evidence content or opaque blobs, operation closure, full payloads/environments, and mechanical Core-ID copies are prohibited.

14. **Claim boundary.** The experiment can test exact derivability, independent native agreement, representation equivalence, and strictness for the frozen profile and fixtures. It cannot evaluate all PROV extensions, every PROV component or serialization, every domain, or whether PROV in general can encode additional facts.

15. **Independent implementation.** RDFLib 7.6.0 is frozen for native PROV-O Turtle/RDF parsing. Candidate PROV-N parsing and normalization will be experiment-owned and will not call RDFLib.

16. **Third-party freeze.** RDFLib 7.6.0; tag commit `8b32146a0f9cb748c2068662e50d02b42fc86dfd`; wheel SHA-256 `30c0a3ebf4c0e09215f066be7246794b6492e054e782d7ac2a34c9f70a15e0dd`; BSD-3-Clause; PyPI release 2026-02-13 with active maintainers as of access. Its transitive parser dependency is pyparsing 3.3.2, wheel SHA-256 `850ba148bd908d7e2411587e247a1e4f0327839c40e2e5e6d05a007ecc69911d`, MIT. Both local wheels are used offline and neither is a semantic authority.

17. **Isolation.** One actual deterministic generator will synchronously notify two collectors. Native may read callbacks and emit qualified PROV-O but may not import Core, read Snapshots, candidate output, or expected answers. Candidate accepts only `ValidatedSnapshot` and may not read native output, receipts, expected answers, or persistent crosswalks. Static imports, runtime read traces, adversarial isolation controls, and separate normalizers will enforce the boundary.

## Decision before implementation

The official reference is available, the requested GeneratedOrigin collapse is consistent with the declared profile, ExplicitDisposition must not be treated as Invalidation, and the independent dual-path design is implementable without a Core change. Implementation may proceed only after this audit commit exists.
